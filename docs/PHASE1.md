# Swachh Safar — Phase 1: Offline-First Registration

## Architecture

```
React UI (pages/Register.jsx)
  ├─ registrationService ──► SQLite (Web Worker, OPFS SAH-pool VFS) ── swachh_safar_local.db
  │                              users · sync_outbox · sync_meta
  └─ syncService ──────────► Firebase Auth (email/password) + Firestore app_users/{uuid}
Service worker (src/pwa/serviceWorker.js): precached app shell incl. sqlite3.wasm, no runtime caching
```

| Concern | Implementation |
|---|---|
| Local DB | `@sqlite.org/sqlite-wasm` in a dedicated worker ([sqlite.worker.js](../src/database/sqlite.worker.js)) using the **opfs-sahpool** VFS. Persists in the Origin Private File System and needs no COOP/COEP headers. |
| Schema | [migrations.js](../src/database/migrations.js), versioned with `PRAGMA user_version`. v1 = spec tables, v2 = sync-tracking columns, `sync_meta`, and a unique index allowing one open outbox op per entity. |
| Password verifier | PBKDF2-HMAC-SHA256, 600,000 iterations, 16-byte random salt ([passwordHash.js](../src/utils/passwordHash.js)). Stored only in SQLite and never sent anywhere. |
| Cloud profile | Firestore `app_users/{localUUID}` with `uuid, auth_uid, username, email, registered_at, account_status, source, synced_at`. The rules reject any other field. |
| Existing data | The `users`, `trains`, `journeys` and `staff_allot` collections and their rules are unchanged. |

## Registration workflow

1. The form validates input: email is trimmed and lowercased; the password must be 8–128 characters with a letter and a digit, and not a common password.
2. The local duplicate check runs, backed by `UNIQUE(email)`.
3. A PBKDF2 hash and salt are created. **One SQLite transaction** inserts the `users` row and the `sync_outbox` row (operation `register`). The outbox payload holds only `id, username, email, created_at`.
4. **Offline:** the app shows *"Registration saved locally. Waiting for internet synchronization."* The record shows as *Pending sync* and is never shown as registered.
5. **Online:** the app syncs immediately with the password it already has in memory.

## Synchronization

**Triggers:** app startup, the `online` event, returning to the foreground (`visibilitychange`), the **Sync now** button, and automatic backoff retries (15 s doubling, up to 10 min).

Firebase needs the plaintext password, and it is never stored. A pending item can therefore sync only when one of these holds:
- The user re-enters the password. A dialog asks automatically once the app is online. The password is checked against the local hash first, so a typo can never create a Firebase account, and it is kept **only in memory** until the sync finishes.
- A Firebase session already exists for that email. This happens when the account was created but the profile write failed, and that sync then finishes with no password.

**Per-item steps:**
1. Atomically claim the item (`pending → processing`).
2. `createUserWithEmailAndPassword`. On `auth/email-already-in-use`, sign in with the same password instead of creating an account. If the password doesn't match, the item becomes a **conflict**: no account is created, it is marked failed, and a *Try again* action appears.
3. If a profile already exists for this Auth UID (registered on another device), link to it. Otherwise `setDoc(app_users/{uuid})`, which is idempotent.
4. Mark the user `registered/synced` and the outbox `completed`, then store `last_sync_at`.

**Failures:** network errors, timeouts (20 s), rate limits and `permission-denied` put the item back to `pending` with `retry_count + 1` and `last_error`. Rejections that need user action (`conflict`, invalid email, disabled account) set it to `failed`. Local rows are never deleted. Items left in `processing` by a closed app return to the queue on startup. Only one sync runs at a time, enforced by an in-process guard plus Web Locks.

## Running

```bash
npm install
npm run dev               # dev server (service worker disabled in dev)
npm run build && npm run preview   # production build with the PWA on http://localhost:4173
```

`.env.local` holds the Firebase Web app config. It was generated by `node scripts/register-web-app.mjs`, which uses the admin service-account key in the repo root. That key is used **only** by the scripts and tests, never bundled, and is in `.gitignore`.

Firestore rules: edit [firestore.rules](../firestore.rules), then run `node scripts/deploy-firestore-rules.mjs --deploy`. The script prints the rollback command for the previously released ruleset.

## TEST 7 — Android device (manual)

OPFS and service workers require HTTPS, or `localhost`.

1. Deploy over HTTPS. With Firebase Hosting (config already in `firebase.json`):
   `npm run build && npx firebase-tools login && npx firebase-tools deploy --only hosting --project swachh-safar`
   The app is then at `https://swachh-safar.web.app`.
   *For quick LAN testing instead:* run `npm run preview`, then on a USB-connected phone use `chrome://inspect` → *Port forwarding* 4173 → `localhost:4173`.
2. On the phone, open the URL in Chrome and wait for *Local database: Ready · persistent*.
3. Use Chrome menu → **Install app** (or *Add to Home screen*), then launch it from the home-screen icon. It opens standalone, without the browser UI.
4. Turn on **Airplane mode**, then force-close and relaunch the app. The screen should load and show *Offline*.
5. Register a new email. Expect *"Registration saved locally…"* and *Pending sync: 1*.
6. Force-close and relaunch the app (still offline). The record is still listed.
7. Turn Airplane mode off. A password dialog appears. Enter the password, and the record changes to **Synced**.
8. Confirm in the Firebase console: Authentication → Users, and Firestore → `app_users`.

## Known limitations

- The OPFS SAH-pool VFS allows **one open connection per origin**. A second tab shows *Local database: Unavailable* until the first closes. This is normal for an installed PWA.
- After an offline registration the password must be re-entered once online. This is by design: it is never stored.
- `navigator.onLine` can report *online* behind captive portals. Requests then fail and are retried, and nothing is lost.
